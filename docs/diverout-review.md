# Diverout 逆向方案檢視與本 App 差距分析

對象：Gemini 提出的〈Diverout 水下影像與影片增強演算法逆向推導方案〉。
做法：方案中的六項黑盒探針全部實作（`scripts/probe-materials.ts`、
`scripts/probes.ts`），先用在**本 App** 上量出目前的表現，並做成可拿去跑
Diverout 的測試包（`scripts/probe-kit.ts`），兩者用同一套指標比較。

> 數字為 OKLab ΔE（越低越接近真實色彩；0.02 約為肉眼可辨門檻）與 8-bit 色階。
> 色卡與深度探針有已知的真實顏色，另外計算「物理上限」：以完全正確的水質、
> 深度與曝光反解成像模型所能得到的結果——任何 App 超過這個程度的紅色都是
> 「生成」而非還原。

## 一、結論

1. **方案的黑盒部分（軌道二）可行且有用**；白盒部分（軌道一）不建議執行，理由見下。
2. 用同一組探針量本 App，**時間穩定、空間一致、灰階中性**都已達標；
   主要差距在三處：
   - **色彩偏淡、偏暗**（色卡 ΔE 0.081，物理上限≈0；彩度 −0.032、亮度 −0.025）——
     這正是「看起來不如 Diverout 鮮豔」最可能的原因；
   - **非水下／漸層內容被過度拉伸**：全自動把中性灰階 0–16 壓成全黑、192 以上推到
     252–255；黑點是硬切，漸層上一個輸入階會跳 5–9 個輸出階（水色背景會出現斷層）；
   - **近距離主體在「遠景水色佔滿畫面」時幾乎沒被校正**（1 m 紅色物體 0.201 → 0.196），
     Sea-thru 只改善到 0.175；遠處（10–20 m）的紅色在物理上已不存在，不應追求。
3. 下一步建議：先用測試包跑 Diverout 取得同條件數字，再依差距調整（見第五節）。

## 四、建議的改進（依優先順序）

1. **色彩還原的彩度與亮度**：以水下色卡（本探針）＋EUVP 真實照片一起當調校目標，
   提高自動彩度與中間調亮度，目標色卡 ΔE ≤ 0.05，同時不讓真實照片 ΔE 變差、
   不增加裁切。這是最直接影響「好不好看」的一項。
2. **柔性黑點（toe）＋依水下程度限制拉伸**：黑點改成和高光一樣的柔性肩部，
   漸層單步跳動 ≤ 3 階；「不是水下」或直方圖本來就滿的畫面，不再做大幅色階拉伸
   （灰階 192 不應變 252）。
3. **近距離主體的空間化校正**：用穿透率／深度圖讓紅色補償隨距離變化，並限制遠處
   的增益（Sea-thru 1.0 在 10–20 m 反而變差）；目標 1 m 物體 ΔE ≤ 0.10。
4. **量測閉環**：每次調整都跑 `scripts/probes.ts`、EUVP 與現有 GPU 驗證，避免改善一項、
   退步另一項。

## 五、怎麼用測試包比較 Diverout

1. 測試包在 `docs/probe-kit/`（13 張 PNG、3 段 H.264 MP4，約 3 MB），傳到 iPhone。
2. 在 Diverout 中以**預設強度**逐一處理，**用最高畫質存回**（相機設定「最相容」→ JPEG；
   不要截圖），檔名保持原名（副檔名可不同）。
3. 把結果放在一個資料夾，執行：
   ```bash
   node --experimental-strip-types scripts/probe-kit.ts compare docs/probe-kit <Diverout輸出資料夾>
   ```
   會列出 Diverout 與本 App 在每一項的數字（讀影片需要 ffmpeg：`brew install ffmpeg`）。
4. 你自己的實拍：把同一張原始照片與 Diverout 結果命名為 `名稱-before.jpg`／`名稱-after.jpg`，
   執行 `npm run analyze <資料夾>`，得到它的色調曲線、色彩矩陣與是否為空間運算。

只要量測 Diverout 的**輸出**來調整我們自己的參數，就不涉及對方的程式或模型。

## 六、Diverout 實測結果（照片增強＋影片一般／超高，2026-10）

測試包交給 Diverout 處理後，用 `probe-kit.ts compare` 與 `npm run analyze` 量測。
照片存成 JPEG（副檔名 .png），影片維持 1024×576、31 幀、30 fps，可逐幀對齊。

|---|---|---|

| 1 灰色色塊彩度 | 0.113（嚴重偏色） | **0.012** |
| 1 漸層列間差異／最大單步 | 0.0 / 1.5 階 | 0.8 / 8.5 階 |

| 3 中性灰階改變 | **0.002** | 0.101 |

**推得的運作方式**（轉換函數擬合）：

- **逐像素、全畫面一套轉換**：漸層列間差異 0、白點無擴散、翻轉等變，沒有局部或深度運算。
- **每個通道各自做色階拉伸**：有亮部與暗部的寫實畫面（6-scene-surface），輸出幾乎完全是
  「每通道線性增益＋黑點」（R² 0.987；增益 R 1.57、G 1.40、B 1.36）——這就是「鮮豔有力」的來源。
- **從綠色借紅（Ancuti 式紅色補償）**：純綠漸層輸出的紅 = 0.53 R + 0.54 G − 0.23 B。
- **沒有場景判斷**：陸地照片同樣被套用；低對比的畫面（色卡、深度、測試影片）會被拉到大面積裁切、
  雜訊放大。
- **影片逐幀獨立處理**，畫面穩定（平均色抖動 0.23 階／幀），但同一套拉伸在測試影片上裁切了九成畫面。

**對本 App 的意義**：Diverout 好看的部分來自「每通道拉滿＋紅色補償」帶來的對比與彩度——對應到
本 App 的改進第 1 項（色彩偏淡偏暗）。它的缺點（大面積裁切、雜訊放大、陸地照片變色、遠處變黑）
是本 App 目前已避開的。合理的方向是：保留現有的準確度與保護機制，加入受控的每通道拉伸
（以百分位數取黑白點、柔性肩部防裁切、依水下程度與雜訊調整強度），讓近景主體與整體對比更有力。

測試素材是合成畫面，差異會被放大；真實潛水照片通常本來就有亮部與暗部，Diverout 的拉伸會溫和許多。
用你自己的實拍 before／after 跑 `npm run analyze`，可以量到它在真實素材上的實際增益。

## 七、已實作：全自動-Diverout／Diverout+（`src/engine/diverout.ts`）

- **擬合**：在寫實探針（水下場景、水面高光場景、陸地、色卡、深度、灰階）上比較多種候選流程，
  最接近 Diverout 輸出的是「從綠色補紅（α 0.2）＋每通道 1.2 %／96 % 百分位拉伸、超出裁切」：
  寫實水下場景誤差 34 階（不處理 81）、水面高光場景 10 階（不處理 14）。直方圖等化可解釋單色與灰階
  探針，但無法同時解釋寫實畫面，故未採用；低對比的合成畫面仍無法吻合——這是**近似**，不是複製。
- **全自動-Diverout**：上述轉換，其餘步驟全關（保留 Diverout 原始設定）。
- **全自動-Diverout+**：黑白點 0.5／99.5 %、每通道增益上限 2.5（雜訊越多越低，最低 1.3）、
  柔性肩部與暗部、依紅光流失程度啟用（陸地照片不動）、開闊水域保留水色（與水色相近的像素少拉 40 %，
  否則每通道拉伸會把藍水拉成灰色；代價是與水色相近的物體校正較少，物體 ΔE 0.122 → 0.137）；疊在本 App 自己的色彩／影調上會重複校正
  （1 m 物體 0.238），所以單獨使用，只保留降噪／銳化／畫質修復自動。
- **色彩校正強度 0–200 %**：兩種模式的套用量。

## 八、一次辨識：拼圖探針 `0-sheet.png`（AI 照片增強試用次數有限時）

`docs/probe-kit/0-sheet.png`（3080×1960）把 12 種探針拼成一張，一次處理就能量：

| 格 | 內容 | 量什麼 |
|---|---|---|
| ①藍水 8 m ②綠水 6 m ③混濁 5 m ④閃燈 10 m ⑤淺水陽光 2.5 m（光束＋水面）⑥深水 15 m | 同一場景、六種水況（已知真值） | 每種水況的色彩誤差、裁切；若 App 依內容處理，可看出它對不同場景的判斷 |
| ⑦ 水下色卡 | Macbeth 24 色，6 m／2 m 藍水 | 色卡 ΔE、灰塊彩度 |
| ⑧ 深度階梯 | 同一紅色物體 1／5／10／20 m | 遠處紅色是否補更多（深度感知） |
| ⑨ 灰階＋純色漸層 | 無色灰階、R/G/B/C/灰漸層 | 中性是否保持、斷階 |
| ⑩ 陸地照片 | 非水下 | 應幾乎不改 |
| ⑪ 脈衝 | 青底 3×3 白點 | 影響半徑（感受野） |
| ⑫ ＝ ①，放在另一個位置 | 重複格 | 輸出不同 ⇒ App 有位置先驗 |

**限制（重要）：** 如果 App 對整張圖只判斷一次場景、套一個全域轉換（Diverout 照片增強實測就是這樣），
12 格都會得到同一個處理，拼圖只能證明「它是全域的」，看不到各場景的個別反應。
所以報告第一步先判定：

- **情境相依度**：同一個輸入顏色在不同格是否被改得一樣（leave-one-out，每格對 32³ 色彩格的平均變化 vs 其他格）。
  < 1.5 ⇒ 全域逐點轉換；1.5–4 ⇒ 部分依內容；> 4 ⇒ 依內容／局部處理（每格是獨立量測）。
- **重複格 ①／⑫ 差異**：位置先驗。

自我測試：不改 0.0、全自動-Diverout 0.7（全域）、本 App 全自動 2.7（部分依內容：局部對比與去霧）、逐格不同處理 9.0；每格抹掉四分之一（模擬生成式）重繪區塊 33%，其他皆 0%。

用法：

1. 用 App 的 AI 照片增強處理 `0-sheet.png` 一次，用最高畫質存檔，不要裁切、不要截圖。
2. `npm run probe-sheet -- compare <輸出檔>`（需要 Chrome 解碼；找不到時設 `CHROME_PATH`）。
3. 若判定為「全域」，依報告建議的順序（②綠水 → ④閃燈 → ⑤淺水陽光 → ⑥深水 → ③混濁）
   逐張處理 `docs/probe-kit/sheet-tiles/NN-*.png`，用 `npm run probe-sheet -- compare-tile <格號> <輸出檔>` 量測。

### 實測：Diverout AI 照片增強「水色重生」（2026-10）

`npm run probe-sheet -- compare <輸出>`：

| 項目 | 結果 |
|---|---|
| 輸出解析度 | 1282×816（1.0 MP；輸入 3080×1960 = 6 MP）— 生成式影像模型的典型輸出大小 |
| 判定 | 依內容處理（情境相依度 16.2 階）；①／⑫ 同圖換位置差 5.1 階（會看周圍內容） |
| 結構 | 重繪區塊平均 2%：物件位置都保留，但 ③ 混濁中的淡魚被抹掉（7%），⑩ 陸地的白卡被抹除、補成沙地（3%） |
| 風格（水下 7 格） | 紅色幾乎清空（平均 R 48→13）、色相轉為青色 195°、彩度 ×1.31、反差 ×1.69、略提亮 |
| 色彩還原 | 變差：對真值色差 0.48→0.72；色卡 ΔE 0.116→0.124；灰塊彩度 0.097 |
| 深度 | 無深度補償（20 m 紅色 ΔE 0.26→0.31） |
| ⑨ 灰階 | 被「理解」成天空：中性灰變藍天漸層、純色漸層變成飽和色帶、灰色列變洋紅（35% 裁切） |
| ⑩ 陸地 | 天空被改成水色，沙地偏綠（ΔE 0.094） |
| ⑪ 脈衝 | 深青背景被拉到亮青（128→233），白點幾乎消失 |

結論：「水色重生」是**語意式的風格化**（把畫面重畫成鮮豔的熱帶青色海水），不是色彩還原；
它會依內容判斷（灰階當天空、白卡當瑕疵），並會局部抹除或補畫。可以仿它的「色調」
（曲線＋3D LUT＋局部對比），但抹除／補畫與語意判斷無法以傳統演算法重現。

新增的指標：**重繪區塊**（24 px 區塊中，輸入或輸出有明顯邊緣但兩者不相關的比例；
局部增強保留邊緣位置，生成式模型會增減或移動物件）、**非逐點變化**（輸出與該格最佳逐點對應
的差，扣掉不改時的基準）、**風格**（OKLab 亮度、彩度比、反差比、色相）。
多個模式可以並列：`npm run probe-sheet -- modes 水色重生.jpg 喚回溫度.jpg …`。
